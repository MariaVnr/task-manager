# ADR-0003: Вибір системи керування базами даних

## Context

Task Manager - це застосунок, який використовує модульну монолітну архітектуру. Для зберігання даних системи необхідно обрати систему керування базами даних (СУБД).

Відповідно до ER-моделі, основними сутностями є User і Task, між якими існує зв'язок один-до-багатьох. Кожне завдання належить конкретному користувачеві.

База даних повинна забезпечувати збереження даних, підтримку зв'язків між сутностями, цілісність даних, виконання транзакцій і можливість ефективного пошуку та фільтрації завдань.

## Considered Options

- **PostgreSQL** - об'єктно-реляційна система керування базами даних з підтримкою SQL, транзакцій, обмежень цілісності та різних типів індексів.

* **MySQL** - реляційна система керування базами даних, яка підтримує SQL, транзакції та зовнішні ключі.
* **SQLite** - вбудована реляційна система керування базами даних, яка зберігає дані у файлі та не потребує окремого серверного процесу.

## Decision

Обираю **PostgreSQL** як систему керування базами даних для Task Manager.

PostgreSQL відповідає потребам проєкту, оскільки підтримує реляційну модель даних, первинні та зовнішні ключі, обмеження цілісності, транзакції й індекси.

Це дозволить забезпечити коректність зв'язку між користувачами та їхніми завданнями, а також ефективно реалізувати операції створення, редагування, видалення, пошуку та фільтрації даних.

PostgreSQL добре підходить для інтеграції з Node.js і забезпечує можливість подальшого розширення системи без необхідності змінювати обрану СУБД.

## Consequences

- Good: підтримка реляційної моделі даних і зв'язків між сутностями.

* Good: забезпечення цілісності даних за допомогою первинних і зовнішніх ключів та обмежень.
* Good: підтримка транзакцій для виконання узгоджених операцій із даними.
* Good: підтримка індексів для оптимізації пошуку та фільтрації завдань.
* Good: можливість використання PostgreSQL у подальших версіях і розширеннях системи.
* Bad: необхідність встановлення та налаштування окремого серверного процесу бази даних.
* Bad: необхідність керувати підключенням до бази даних і налаштовувати її для локального середовища розробки та тестування.

## Pros and Cons of the Options

### PostgreSQL

- Good: підтримка транзакцій, зовнішніх ключів та обмежень цілісності.
- Good: широкі можливості індексації та оптимізації запитів.
- Good: підтримка різних типів даних і розширених можливостей SQL.
- Bad: потребує окремого налаштування та запуску сервера бази даних.

### MySQL

- Good: підтримка реляційної моделі даних, транзакцій і зовнішніх ключів.
- Good: поширена СУБД із великою кількістю документації та інструментів.
- Bad: має власні особливості SQL і типів даних, які потрібно враховувати під час розробки.

### SQLite

- Good: проста початкова конфігурація, оскільки не потребує окремого сервера бази даних.
- Good: зручна для невеликих локальних застосунків і тестових середовищ.
- Bad: має обмеження щодо одночасного виконання операцій запису порівняно з повноцінними серверними СУБД.
- Bad: менш зручна для сценарію, у якому база даних має працювати як окремий серверний компонент застосунку.
