# ADR-0001: Вибір архітектури системи

## Context

Task Manager - це застосунок для керування особистими завданнями користувачів. Система передбачає реєстрацію та авторизацію користувачів, створення, перегляд, редагування й видалення завдань, а також пошук і фільтрацію.

Необхідно обрати архітектуру, яка забезпечить зрозумілу організацію коду, розділення відповідальності між компонентами та можливість подальшого розширення системи.

## Considered Options

- **Монолітна архітектура (Monolithic Architecture)** - усі компоненти системи реалізовані в межах одного застосунку без чіткого розділення на незалежні функціональні модулі.
- **Модульний моноліт (Modular Monolith)** - система є єдиним застосунком, але її функціональність розділена на окремі модулі з чітко визначеною відповідальністю.
- **Мікросервісна архітектура (Microservices)** - система складається з окремих незалежних сервісів, кожен із яких відповідає за певну частину функціональності.

## Decision

Обираю **модульний моноліт (Modular Monolith)**, оскільки він забезпечує чіткий розподіл відповідальності між модулями, зберігаючи простоту розробки, запуску, розгортання та тестування єдиного застосунку.

Мікросервісна архітектура створила б надлишкову складність для навчального проєкту, який розробляє один розробник. Вона потребувала б додаткової організації мережевої взаємодії між сервісами, їхнього окремого розгортання та вирішення питань узгодженості даних без суттєвої користі для поточного масштабу системи.

Звичайний моноліт без чітких меж між функціональними частинами також не є оптимальним варіантом, оскільки зі збільшенням кількості функцій логіка різних частин системи може переплітатися, що ускладнить підтримку та тестування.

Система буде реалізована як один застосунок з однією базою даних. Функціональність буде розділена на такі модулі:

- `auth` - реєстрація та авторизація користувачів;
- `tasks` - керування завданнями та реалізація пов'язаної з ними бізнес-логіки.

Модулі взаємодіятимуть через внутрішні виклики без мережевої взаємодії між ними. Перелік модулів, їхня відповідальність і дозволені залежності будуть описані в `spec.md`.

Дотримання меж між модулями планується перевіряти автоматично за допомогою команди `make check`.

## Consequences

- Good: чітке розділення функціональності на модулі.

* Good: простіша розробка, запуск і тестування порівняно з мікросервісною архітектурою.
* Good: можливість розвивати окремі частини системи незалежно на рівні коду.
* Bad: модулі залишаються частинами одного застосунку та не можуть розгортатися незалежно один від одного.
* Bad: порушення меж між модулями може призвести до тісного зв'язування компонентів.

## Pros and Cons of the Options

### Монолітна архітектура (Monolithic Architecture)

- Good: проста початкова структура та швидкий запуск розробки.
- Good: нескладне розгортання й тестування.
- Bad: зі збільшенням функціональності код може ставати складнішим для підтримки.
- Bad: відсутність чіткого розділення відповідальності може ускладнити розвиток системи.

### Модульний моноліт (Modular Monolith)

- Good: чіткий поділ системи на функціональні модулі.
- Good: простіше підтримувати та розширювати код.
- Good: усі модулі працюють у межах одного застосунку, тому не потрібна окрема інфраструктура для взаємодії між сервісами.
- Bad: необхідно дотримуватися меж і відповідальності модулів.
- Bad: неможливо розгортати та масштабувати окремі модулі незалежно від усього застосунку.

### Мікросервісна архітектура (Microservices)

- Good: незалежна розробка, розгортання та масштабування окремих сервісів.
- Good: можливість використовувати різні технології для окремих сервісів.
- Bad: складніша організація взаємодії між сервісами.
- Bad: потребує додаткової інфраструктури та складнішого налаштування.
- Bad: надмірна складність для поточного масштабу Task Manager.
