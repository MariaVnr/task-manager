# ADR-0004: Вибір механізму автентифікації

## Context

Task Manager передбачає реєстрацію користувачів, вхід до системи, ідентифікацію поточного користувача та вихід із системи.

Проєкт розробляється одним розробником на Node.js з використанням Express.js і PostgreSQL. Основним клієнтом передбачається браузер, а підтримка мобільних і сторонніх клієнтів наразі не є вимогою.

Необхідно обрати механізм автентифікації, який забезпечить безпечне зберігання облікових даних, контроль доступу до сесій і можливість завершення сесії користувача.

## Considered Options

- Серверні сесії з використанням cookie.
- JWT (access token + refresh token).
- Непрозорі токени (Opaque Tokens).

## Decision

Обрано: серверні сесії з використанням cookie та зберіганням даних сесій у PostgreSQL, оскільки цей підхід відповідає поточним вимогам проєкту, спрощує реалізацію виходу із системи та дає змогу відкликати сесію без додаткових механізмів.

JWT розглядався першим як рекомендований варіант, але відхилений: для одного браузерного клієнта його переваги (робота з мобільними й сторонніми клієнтами) не потрібні, а відкликання токенів, ротація refresh-токенів і безпечне зберігання додають складність і ризики безпеки.

Паролі зберігаються виключно у вигляді хешів із використанням Argon2id. Bcrypt не обрано, оскільки Argon2id є сучаснішим алгоритмом, стійким до атак на спеціалізованому обладнанні.

Модуль auth відповідає за реєстрацію, автентифікацію, створення та завершення сесій, а також надання ідентифікатора поточного користувача іншим модулям. Модуль tasks використовує цей ідентифікатор для перевірки належності завдань користувачу.

## Consequences

- Good: завершення сесії та відкликання доступу відбувається видаленням запису зі сховища.
- Good: ідентифікатор сесії недоступний JavaScript у браузері завдяки `HttpOnly`.
- Good: PostgreSQL уже є основною БД, окреме сховище сесій не потрібне.
- Good: не потрібно реалізовувати підпис, оновлення й відкликання JWT.
- Good: автентифікацію можна тестувати HTTP-запитами зі збереженням cookie.
- Bad: кожен автентифікований запит потребує звернення до БД для перевірки сесії.
- Bad: cookie потребують захисту від CSRF-атак.
- Bad: потрібно налаштувати термін дії сесій і очищення прострочених записів.
- Bad: для мобільних і сторонніх клієнтів, а також для API на іншому домені, знадобиться додаткове налаштування (CORS, cookie) або інший механізм.

## Pros and Cons of the Options

### Серверні сесії з використанням cookie

- Good: простий механізм для браузерного клієнта.
- Good: негайне завершення сесії та відкликання доступу.
- Good: не потрібно зберігати токени в `localStorage` чи ротувати refresh-токени.
- Bad: потрібне серверне сховище сесій.
- Bad: необхідний захист від CSRF.
- Bad: менш зручний для мобільних і сторонніх клієнтів.

### JWT (access token + refresh token)

- Good: зручний для SPA, мобільних і сторонніх клієнтів.
- Good: access token перевіряється без звернення до БД.
- Bad: потрібно безпечно зберігати токени й керувати їхнім терміном дії.
- Bad: потрібні оновлення й ротація refresh-токенів.
- Bad: дострокове відкликання access token складне.

### Непрозорі токени (Opaque Tokens)

- Good: випадкові токени не містять даних користувача.
- Good: негайне відкликання видаленням запису з БД.
- Bad: кожен запит потребує звернення до сховища.
- Bad: керування токенами, їхнім терміном дії та зберіганням потрібно реалізовувати самостійно.
- Bad: для браузерного сценарію не мають переваг над серверними сесіями.

## Security Considerations

- Паролі зберігаються лише як хеші Argon2id.
- Cookie має прапорці `HttpOnly`, `Secure` і `SameSite=Lax`.
- Після успішного входу ідентифікатор сесії оновлюється (захист від session fixation).
- Для маршруту входу передбачається обмеження частоти запитів.
- Для запитів, що змінюють стан системи, потрібен захист від CSRF.
- У production-середовищі використовується HTTPS.
- Ідентифікатор користувача для роботи із завданнями береться з перевіреної сесії, а не з тіла чи параметрів запиту.
- Для кожної операції із завданнями перевіряється належність запису поточному користувачу.
