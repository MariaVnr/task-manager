# ADR-0002: Вибір мови програмування і фреймворку

## Context

Task Manager розробляється з використанням архітектури модульного моноліту.

Необхідно обрати мову програмування та вебфреймворк, які забезпечать реалізацію серверної логіки, обробку HTTP-запитів, маршрутизацію та взаємодію з базою даних.

## Considered Options

**Мови програмування:**

- **JavaScript (CommonJS) ** - мова програмування, яка виконується на сервері за допомогою Node.js.
- **TypeScript** - мова програмування на основі JavaScript зі статичною типізацією, яка компілюється в JavaScript.

**Вебфреймворки:**

- **Express.js** - мінімалістичний вебфреймворк для Node.js, який надає засоби маршрутизації та обробки HTTP-запитів.
- **Fastify** - вебфреймворк для Node.js, орієнтований на продуктивність і систему плагінів.
- **NestJS** - вебфреймворк для Node.js з готовою модульною структурою та визначеними підходами до організації застосунку.

## Decision

Обираю JavaScript (CommonJS) на Node.js з фреймворком Express.js.

JavaScript обрано, тому що він не потребує етапу компіляції й додаткових правил типізації, а наявний конвеєр (ESLint із `sourceType: 'commonjs'`, `node:test`, збірка як перевірка завантаження) працює без змін. Node.js є середовищем виконання для обраних мови й фреймворку, а не окремим варіантом вибору.

Express.js обрано, тому що він має найбільше навчальних матеріалів і вимагає мінімум нових концепцій. Fastify розглядався як рекомендований варіант через вбудовану валідацію й плагінну модель, але його інкапсуляція плагінів додає концепції, які для початківця є зайвим навантаженням. Межі модулів auth і tasks у будь-якому разі забезпечуються правилами імпортів, а не фреймворком, тож ізоляція плагінів Fastify не дає вирішальної переваги. NestJS не обрано через орієнтацію на TypeScript і надмірний шаблонний код для двох модулів
Express.js не нав'язує жорсткої структури проєкту, тому дозволяє самостійно організувати код відповідно до обраної архітектури модульного моноліту.

TypeScript не обирається для поточної версії, щоб не ускладнювати початкове налаштування та розробку додатковими інструментами й правилами типізації.

## Consequences

- Good: конвеєр якості працює без переробки.
- Good: мінімум нових концепцій дозволяє зосередитися на HTTP, автентифікації та роботі з БД.
- Good: велика кількість документації та готових відповідей на типові помилки.
- Good: гнучкість Express дозволяє організувати модулі відповідно до ADR-0001.
- Bad: JavaScript не дає статичної перевірки типів, помилки типів виявляються під час виконання або тестування.
- Bad: структуру модулів і правила залежностей потрібно підтримувати самостійно, фреймворк цього не забезпечує.
- Bad: валідацію запитів доведеться підключати окремою бібліотекою.

## Pros and Cons of the Options

### JavaScript

- Good: простіший початок роботи, не потребує компіляції.
- Good: наявний конвеєр уже налаштований під нього.
- Bad: помилки типів виявляються лише під час виконання або тестування.

### TypeScript

- Good: статична типізація виявляє частину помилок ще під час розробки.
- Good: типи полегшують підтримку великих проєктів.
- Bad: потребує додаткового налаштування й переробки конвеєра.
- Bad: додає етап компіляції.

### Express.js

- Good: мінімалістичний і гнучкий, найбільше навчальних матеріалів.
- Good: прості засоби маршрутизації та middleware.
- Bad: структуру й правила організації коду потрібно визначати самостійно.
- Bad: валідація запитів не вбудована.

### Fastify

- Good: вбудована валідація через JSON Schema, плагінна модель, висока продуктивність.
- Good: зручне тестування через `inject()` без запуску сервера.
- Bad: потребує освоєння інкапсуляції плагінів, менше навчальних матеріалів.
- Bad: ізоляція плагінів не замінює перевірки імпортів між модулями.

### NestJS

- Good: готова структура модулів і компонентів.
- Good: підтримка TypeScript та інструментів для великих застосунків.
- Bad: багато абстракцій і шаблонного коду для двох модулів.
- Bad: орієнтований на TypeScript, на чистому JavaScript незручний.
