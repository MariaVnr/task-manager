## 1. Призначення проєкту

**Назва:** Task Manager
**Мета:** надати користувачам можливість планувати власну діяльність, відстежувати виконання завдань і контролювати терміни їх виконання.
## 2. Features

**Feature 1:** Реєстрація і вхід користувача
**Feature 2:** Створення нових завдань.
**Feature 3:** Перегляд списку завдань.
**Feature 4:** Редагування завдань 
**Feature 5:**  Видалення завдань.
**Feature 6:** Зміна статусу виконання завдань (todo, in_progress, done).
**Feature 7:** Встановлення пріоритету завдань (low, medium, high)
**Feature 8:** Встановлення термінів виконання (дедлайнів).
**Feature 9:** Пошук завдань (за ім’ям, за датою)
**Feature 10:** Фільтрація завдань (за датою, за ім’ям, за статусом, за пріоритетом)  
## 3. Архітектура системи

В проекті використовуємо такий архітектурний підхід, як модульний моноліт (Modular Monolith). Буде реалізовано один Node.js застосунок і одна БД.


## 4. Модель даних 
### Виділені сутності і атрибути:
#### Сутність User
| Атрибут    | Тип даних    | Обмеження        | Призначення                          |
| ---------- | ------------ | ---------------- | ------------------------------------ |
| id         | INT          | PK               | Унікальний ідентифікатор користувача |
| email      | VARCHAR(255) | UNIQUE, NOT NULL | Електронна пошта                     |
| password   | VARCHAR(255) | NOT NULL         | Хеш пароля                           |
| created_at | TIMESTAMP    | NOT NULL         | Дата створення облікового запису     |
#### Сутність Task

| Атрибут     | Тип даних    | Обмеження | Призначення                                |
| ----------- | ------------ | --------- | ------------------------------------------ |
| id          | INT          | PK        | Унікальний ідентифікатор завдання          |
| user_id     | INT          | FK        | Ідентифікатор власника завдання            |
| title       | VARCHAR(255) | NOT NULL  | Назва завдання                             |
| description | TEXT         | NULL      | Детальний опис завдання                    |
| status      | VARCHAR(20)  | NOT NULL  | Статус виконання (todo, in_progress, done) |
| priority    | VARCHAR(20)  | NOT NULL  | Пріоритет завдання (low, medium, high)     |
| deadline    | TIMESTAMP    | NULL      | Термін виконання                           |
| created_at  | TIMESTAMP    | NOT NULL  | Дата створення                             |
| updated_at  | TIMESTAMP    | NOT NULL  | Дата останнього оновлення                  |

Між User та Task встановлюємо зв'язок один до багатьох (1:N). Бо один користувач може мати багато завдань, а кожне завдання може належити лише одному користувачу, бо завдання не може існувати без власника.

## 5. Ключові сценарії

**Сценарій 1. Реєстрація:** 
1. Користувач надсилає email і пароль.
2. Система перевіряє коректність введених даних та унікальність email.
3. Пароль хешується перед збереженням.
4. У базі даних створюється новий запис у таблиці User.
5. Система повертає результат реєстрації.
Помилка: email зайнятий або дані некоректні, тоді запису немає і повідомлення про помилку валідації.

**Сценарій 2. Створення завдання**
1. Користувач надсилає email і пароль.
2. Система знаходить обліковий запис за email.
3. Перевіряється відповідність пароля збереженому хешу.
4. У разі успіху користувач отримує токен доступу, який передає в захищених запитах.
Помилка: якщо невірні дані, то токен не видається; відповідь не розкриває, що саме невірне (email чи пароль).

**Сценарій 3. Авторизація користувача**
1. Авторизований користувач надсилає назву завдання та додаткові параметри: опис, пріоритет і дедлайн.
2. Система перевіряє коректність введених даних.
3. Створюється новий запис у таблиці Task із прив'язкою до користувача через user_id.
4. Якщо статус або пріоритет не вказані, встановлюються значення за замовчуванням: todo та medium.
5. Система повертає створене завдання.
Помилка: порожня назва завдання або дедлайн у минулому, то запису немає.

**Сценарій 4. Отримання списку завдань**
1. Авторизований користувач надсилає запит на отримання списку завдань.
2. Система отримує лише ті завдання, у яких user_id відповідає ідентифікатору поточного користувача.
3. Система повертає список знайдених завдань.

**Сценарій 5. Редагування завдання**
1. Користувач надсилає запит на редагування завдання із зазначенням його ідентифікатора.
2. Система перевіряє існування завдання та належність його поточному користувачу.
3. Перевіряється коректність нових значень.
4. У базі даних оновлюються передані поля та значення updated_at.
5. Система повертає оновлене завдання.
Помилка: чуже або неіснуюче завдання, то повідомлення "не знайдено"; невалідні дані залишаються без змін.

**Сценарій 6. Зміна статусу завдання**
1. Користувач надсилає запит на зміну статусу завдання.
2. Система перевіряє існування завдання, власника та допустимість нового статусу.
3. Значення status оновлюється та updated_at в базі даних.
4. Система повертає результат операції.
Помилка: заборонений перехід, то повідомлення про помилку валідації і статус не змінюється; чуже завдання, то повідомлення "не знайдено".

**Сценарій 7. Видалення завдання**
1. Користувач надсилає запит на видалення завдання.
2. Система перевіряє існування завдання та належність його поточному користувачу.
3. Запис завдання видаляється з бази даних.
4. Система повертає результат видалення.
Помилка: чуже або неіснуюче завдання, то повідомлення «не знайдено» і тоді нічого не видаляється.

**Сценарій 8. Пошук і фільтрація завдань**
1. Користувач надсилає запит із параметрами пошуку або фільтрації.
2. Система виконує пошук серед завдань поточного користувача.
3. Результати фільтруються за заданими параметрами: назвою, статусом, пріоритетом або дедлайном.
4. Система повертає список завдань, що відповідають умовам запиту або порожній, якщо збігів немає. Дані не змінюються.

## 6. Критерії прийняття

**Реєстрація та авторизація**:
- Користувач може зареєструватися, вказавши коректний email і пароль; повторна реєстрація з тим самим email відхиляється.
- У БД зберігається лише хеш пароля; пароль у відкритому вигляді ніде не зберігається і не потрапляє в логи.
- Логін із невірним email або паролем не видає токен, а відповідь однакова в обох випадках.
- Запит до операцій із завданнями без валідного токена відхиляється.

**Керування завданнями**:
- Новому завданню автоматично призначаються статус todo і пріоритет medium, якщо їх не вказано.
- Порожня назва завдання відхиляється.
- Дедлайн у минулому при створенні відхиляється.
- Користувач бачить, змінює й видаляє лише власні завдання; чуже завдання поводиться як неіснуюче.
- Користувач може змінювати статус завдання на одне з допустимих значень: з todo в in_progress в done.
-  Редагування та зміна статусу оновлюють updated_at.
-  Видалене завдання більше не повертається у списку

**Список, пошук і фільтрація**
- Користувач може отримати список власних завдань.
- Пошук повертає завдання, назва яких відповідає пошуковому запиту
- Фільтрація за статусом і пріоритетом повертає лише відповідні завдання.
- Результати пошуку та фільтрації містять лише завдання поточного користувача.
- Якщо відповідних завдань немає, система повертає порожній список.
