## Архітектурні рішення для Task Manager

**Припущення:** це невеликий проєкт (один домен, дві сутності, CRUD із пошуком і фільтрами), невелика команда, навантаження сотні або тисячі користувачів, а не мільйони. Якщо це не так, частину висновків треба переглянути.

### 1. Архітектурний стиль застосунку

**Проблема.** Як організувати код і розгортання: єдиним застосунком чи набором сервісів.

| Варіант           | Переваги                                                                            | Недоліки                                                                                        |
| ----------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Моноліт           | Простота розробки, тестування й розгортання; транзакції «з коробки»                 | Може розростатися без дисципліни; масштабується тільки цілком                                   |
| Модульний моноліт | Один деплой, але чіткі межі модулів (`auth`, `tasks`); легко виділити сервіс згодом | Потрібна дисципліна у залежностях між модулями                                                  |
| Мікросервіси      | Незалежне масштабування й деплой                                                    | Складна інфраструктура, розподілені транзакції, мережеві збої; для двох сутностей це надлишково |

**Вибір: модульний моноліт.** Домен малий, команді не потрібні накладні витрати мікросервісів. Розділення на модулі `auth` і `tasks` дає змогу виділити їх пізніше, якщо виникне потреба.

### 2. Клієнтська частина

**Проблема.** Який тип інтерфейсу потрібен: веб, мобільний чи обидва.

| Варіант                                    | Переваги                                                                                                          | Недоліки                                                         |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| SPA (React/Vue) + API                      | Зручний інтерфейс для фільтрів і зміни статусу без перезавантаження; той самий API підійде для мобільного клієнта | Окремий фронтенд-проєкт, більше коду                             |
| Серверний рендеринг (Django/Rails-шаблони) | Найшвидший старт, менше коду                                                                                      | Складніше розширювати на мобільні застосунки; менш динамічний UI |
| Нативний мобільний застосунок              | Найкращий досвід на телефоні                                                                                      | Дорожче, потребує окремої розробки під платформи                 |

**Вибір: SPA + REST API.** Специфікація не обмежує платформу, а розділення клієнта й API залишає відкритим шлях до мобільного клієнта. Якщо потрібен максимально швидкий MVP, серверні шаблони теж виправдані.

### 3. Стиль API

**Проблема.** Як клієнт спілкується з сервером.

| Варіант | Переваги                                                                 | Недоліки                                                                      |
| ------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| REST    | Простий, загальновідомий, добре кешується, багато інструментів (OpenAPI) | Можливі зайві або недостатні дані у відповіді                                 |
| GraphQL | Клієнт сам обирає поля, один ендпоінт                                    | Складніша реалізація, кешування й захист від важких запитів потребують зусиль |
| gRPC    | Висока продуктивність                                                    | Незручний для браузера, надлишковий тут                                       |

**Вибір: REST.** Ресурси `tasks` і `users` ідеально лягають на CRUD. Фільтри й пошук передаються query-параметрами: `GET /tasks?status=done&priority=high&q=звіт&due_before=2026-12-01`. Список варто робити з пагінацією (`limit`/`offset` достатньо на старті).

### 4. База даних

**Проблема.** Яку СУБД обрати для користувачів і завдань.

| Варіант       | Переваги                                                                          | Недоліки                                                                           |
| ------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| PostgreSQL    | Зв'язки, транзакції, ENUM/CHECK, повнотекстовий пошук і trigram-індекси вбудовано | Трохи складніше адмініструвати, ніж SQLite                                         |
| MySQL/MariaDB | Поширена, проста в хостингу                                                       | Слабший вбудований повнотекстовий пошук, менше можливостей у складних запитах      |
| MongoDB       | Гнучка схема                                                                      | Дані реляційні й фіксовані, перевага схеми не потрібна; слабші гарантії цілісності |
| SQLite        | Нуль адміністрування                                                              | Обмежена паралельність, незручна для багатокористувацького сервісу                 |

**Вибір: PostgreSQL.** ER-модель реляційна, а PostgreSQL закриває пошук і фільтри (Features 9–10) без окремих систем.

### 5. Автентифікація та сесії

**Проблема.** Як підтверджувати особу користувача після входу (Feature 1).

| Варіант                                           | Переваги                                                  | Недоліки                                                                                 |
| ------------------------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Серверні сесії (cookie)                           | Просто, легко анулювати сесію, безпечно при `HttpOnly`    | Потрібне сховище сесій; складніше з мобільними клієнтами                                 |
| JWT (access + refresh)                            | Без стану на сервері, зручно для SPA і мобільних клієнтів | Складно відкликати токен; помилки зберігання (`localStorage`) призводять до вразливостей |
| Зовнішній провайдер (OAuth, Auth0, Firebase Auth) | Не треба зберігати паролі, є вхід через Google            | Залежність від сервісу, інтеграція, можлива вартість                                     |

**Вибір: JWT з коротким терміном життя access-токена та refresh-токеном в** `**HttpOnly**` **cookie.** Це добре поєднується з SPA і майбутнім мобільним клієнтом. Незалежно від варіанту: паролі зберігати лише як хеші (argon2/bcrypt), працювати через HTTPS, а в кожному запиті до завдань перевіряти, що `task.user_id` збігається з поточним користувачем. Якщо хочеться менше власного коду безпеки, зовнішній провайдер теж розумний вибір.

### 6. Пошук і фільтрація

**Проблема.** Як швидко шукати завдання за ім'ям і датою та фільтрувати за статусом і пріоритетом.

| Варіант                                    | Переваги                                    | Недоліки                                                                     |
| ------------------------------------------ | ------------------------------------------- | ---------------------------------------------------------------------------- |
| SQL з B-tree індексами + `ILIKE`           | Найпростіше, нуль додаткової інфраструктури | `LIKE '%...%'` не використовує звичайний індекс, повільно на великих обсягах |
| PostgreSQL trigram (`pg_trgm`) / full-text | Швидкий пошук за підрядком у тій самій БД   | Потрібно налаштувати розширення й індекси                                    |
| Elasticsearch/OpenSearch                   | Потужний пошук, релевантність               | Окремий сервіс, синхронізація даних, надлишково для задачі                   |

**Вибір: SQL з індексами з ER-моделі плюс** `**pg_trgm**` **для пошуку за назвою.** Один користувач має небагато завдань, тож цього вистачить із запасом. Окремий пошуковий рушій виправданий лише якщо з'являться мільйони записів або складна релевантність.

### 7. Розгортання та середовище

**Проблема.** Де і як запускати систему.

| Варіант                        | Переваги                                         | Недоліки                                               |
| ------------------------------ | ------------------------------------------------ | ------------------------------------------------------ |
| PaaS (Render, Railway, Fly.io) | Мінімум адміністрування, швидкий старт           | Вища вартість при зростанні, залежність від платформи  |
| Docker Compose на VPS          | Дешево, повний контроль, відтворюване середовище | Оновлення, резервні копії, моніторинг на вас           |
| Kubernetes                     | Масштабування, відмовостійкість                  | Висока складність, непотрібна для моноліту з однією БД |

**Вибір: Docker-контейнери, для початку PaaS або один VPS із Docker Compose.** Контейнеризація дає однакове середовище в розробці й на продакшені та залишає шлях до Kubernetes. Обов'язково налаштувати автоматичні резервні копії PostgreSQL і CI для тестів.

**Коротко:** Fastify підходить для модульного моноліту, але його плагінна модель ізолює менше, ніж було подано в попередній відповіді. Це ізоляція на рівні екземпляра Fastify, а не коду. Для початківця вибір між Fastify і Express майже рівноцінний, тому вирішальними є практичні фактори.

### 1. Що саме ізолює плагінна модель

Кожен `register()` створює інкапсульований контекст. Усе, що реєструється всередині (декоратори, хуки, маршрути, схеми), видно цьому плагіну та його нащадкам, а сусіднім плагінам і батьківському контексту — ні.

| Аспект                                 | Чи ізолюється | Пояснення                                                          |
| -------------------------------------- | ------------- | ------------------------------------------------------------------ |
| Декоратори й хуки всередині плагіна    | Так           | Хук `onRequest` у `tasks` не вплине на `auth`                      |
| Префікс і набір маршрутів              | Так           | `register(tasks, { prefix: '/tasks' })`                            |
| Порядок завантаження й явні залежності | Так           | Через `fastify-plugin` можна вказати `dependencies: ['auth']`      |
| JavaScript-імпорти між файлами         | Ні            | Ніщо не заважає написати `require('../auth/repository')` у `tasks` |
| Доступ до чужих таблиць у БД           | Ні            | Fastify цього не контролює                                         |

### 2. Поправка до попередньої відповіді

Декоратор, оголошений у `auth`, через інкапсуляцію не видно в `tasks`. Щоб його розшарити, плагін `auth` можна обгорнути в `fastify-plugin`. Це виводить його декоратори в батьківський контекст.

```
// auth/index.js
const fp = require('fastify-plugin')

module.exports = fp(async function auth(fastify) {
  fastify.decorate('authenticate', async (request) => {
    // Перевірка автентифікації
  })
}, { name: 'auth' })

// tasks/index.js
const fp = require('fastify-plugin')

module.exports = fp(async function tasks(fastify) {
  fastify.get('/tasks', { onRequest: [fastify.authenticate] }, handler)
}, { name: 'tasks', dependencies: ['auth'] })
```

Це нормально, але означає, що публічний інтерфейс `auth` (`authenticate`) стає глобально видимим у відповідному контексті. Прихованою залишається лише реалізація, яку не виставили назовні.

### 3. Як насправді тримати межі

У Fastify і Express механізм однаковий:

1. Структура каталогів, де кожен модуль має єдину точку входу (`index.js`).
2. Правило імпортів, яке перевіряє `eslint-plugin-boundaries` або `dependency-cruiser`.
3. Дисципліна роботи з БД: модуль працює лише зі своїми таблицями.

Fastify додає корисний бонус: явні `dependencies` і порядок реєстрації, але автоматичної перевірки імпортів він не замінює.

### 4. Fastify чи Express для початківця

| Критерій                                 | Express                     | Fastify                                                               |
| ---------------------------------------- | --------------------------- | --------------------------------------------------------------------- |
| Матеріали, курси, відповіді на запитання | Найбільше                   | Менше, але документація якісна                                        |
| Концепції для освоєння                   | Мінімум: middleware, Router | Додатково: інкапсуляція, `fastify-plugin`, життєвий цикл, JSON Schema |
| Валідація                                | Окремий пакет (Joi, Zod)    | Вбудована                                                             |
| Тестування                               | `supertest`                 | Вбудований `inject()`                                                 |
| Ізоляція модулів                         | Лише структурна             | Контекст плагіна + явні залежності                                    |
| Типова помилка новачка                   | Хаос у структурі            | Нерозуміння, чому декоратор не видно без `fp`                         |

### 5. Чи виправданий Fastify

**Так, але не однозначно краще.**

- **Обирайте Express**, якщо курс чи викладач використовує його, ви вперше пишете backend і хочете знайти відповідь на помилку за допомогою великої кількості матеріалів.
- **Обирайте Fastify**, якщо метою є вивчити сучасні практики (валідація зі схем, плагіни, структурований підхід) і ви готові витратити час на розуміння інкапсуляції.

Головне - архітектурні межі мають забезпечуватися перевіркою імпортів, а не очікуванням, що фреймворк зробить це сам.

### 3. Чому серверні сесії

1. Вимоги проєкту прості: реєстрація, вхід, доступ до власних завдань і вихід.
2. Видалення запису сесії одразу закриває доступ.
3. Не потрібно вирішувати, де зберігати refresh-токен, як його ротувати та відкликати.
4. PostgreSQL уже є основною БД, тому не потрібно додавати окреме сховище.
5. Механізм «cookie → запис у БД → `user_id`» легко зрозуміти й відлагодити.

### 4. Наслідки рішення

**Переваги:**

- Миттєве завершення сесії та відкликання доступу.
- Секрет недоступний JavaScript у браузері завдяки `HttpOnly`.
- Прості тести та налагодження.
- Менше власного криптографічного коду.

**Недоліки та обмеження:**

- Кожен автентифікований запит потребує перевірки сесії у сховищі.
- Для мобільних і сторонніх клієнтів cookie можуть бути менш зручними.
- Cookie потребують захисту від CSRF.
- Cross-origin SPA потребує налаштування CORS і cookie.
- Потрібно очищати прострочені сесії в БД.

### 5. Ризики безпеки та їх зменшення

| Ризик                              | Як зменшити                                                                 |
| ---------------------------------- | --------------------------------------------------------------------------- |
| Витік паролів із БД                | Зберігати лише хеш (Argon2id або bcrypt)                                    |
| Підбір паролів                     | Rate limit на `/login`, однакова відповідь для невірного email або пароля   |
| Перехоплення cookie                | HTTPS, прапорці `Secure` і `HttpOnly`                                       |
| Викрадення сесії через XSS         | Екранування виводу, уникнення небезпечної вставки HTML, CSP                 |
| CSRF                               | `SameSite=Lax` або `Strict`, CSRF-токен або перевірка `Origin`              |
| Фіксація сесії                     | Генерувати новий ID після входу (`req.session.regenerate`)                  |
| Слабкий ID сесії                   | Використовувати криптографічно випадкові ID, які генерує бібліотека         |
| Вічні сесії                        | Обмежити термін неактивності та абсолютний термін                           |
| Доступ до чужих завдань            | Отримувати `user_id` із сесії та додавати його до кожного запиту до `tasks` |
| Зберігання сесій у пам'яті процесу | Використовувати PostgreSQL-сховище, наприклад `connect-pg-simple`           |
| Витік секретів                     | Зберігати секрет сесії та рядок підключення в змінних середовища            |

### 6. Умови перегляду рішення

Рішення варто переглянути, якщо:

- з'явиться мобільний або сторонній клієнт;
- фронтенд і API опиняться на різних доменах;
- знадобиться кілька екземплярів застосунку без спільного сховища;
- з'явиться вимога входу через Google/GitHub або корпоративний SSO;
- навчальна мета зміниться на вивчення JWT.

### Підсумок

| Питання         | Рішення                                                               |
| --------------- | --------------------------------------------------------------------- |
| Механізм        | Серверні сесії, cookie `HttpOnly; Secure; SameSite=Lax`               |
| Сховище         | PostgreSQL, а не пам'ять процесу                                      |
| Паролі          | Argon2id або bcrypt                                                   |
| Захист          | Rate limit на `/login`, CSRF-захист, `helmet`, нова сесія після входу |
| Доступ до даних | `user_id` лише із сесії, обов'язково в кожному запиті до `tasks`      |
| Перегляд        | Мобільний клієнт, різні домени, кілька екземплярів, зовнішній вхід    |

З сесіями інтерфейс `auth` залишається тим самим за змістом (`getCurrentUserId`), але перевіряє сесію, а не токен. Модульні межі при цьому не змінюються.
