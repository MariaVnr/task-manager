## AI Response

## ER-модель бази даних Task Manager

З вимог випливають дві сутності: **User** (Feature 1) і **Task** (Features 2-10). Статус і пріоритет є атрибутами завдання, а не окремими сутностями, бо мають фіксований набір значень. Теги й категорії в специфікації відсутні, тому я їх не додаю.

### 1. Сутності та атрибути

#### User (користувач)

| Атрибут       | Тип           | Обмеження             | Опис                                      |
| ------------- | ------------- | --------------------- | ----------------------------------------- |
| **user_id**   | BIGINT / UUID | **PK**, auto          | Ідентифікатор                             |
| email         | VARCHAR(255)  | UNIQUE, NOT NULL      | Логін для входу                           |
| username      | VARCHAR(100)  | NOT NULL              | Відображуване ім'я                        |
| password_hash | VARCHAR(255)  | NOT NULL              | Хеш пароля (bcrypt/argon2), не сам пароль |
| created_at    | TIMESTAMP     | NOT NULL, default now | Дата реєстрації                           |

#### Task (завдання)

| Атрибут     | Тип              | Обмеження                                                          | Опис                            |
| ----------- | ---------------- | ------------------------------------------------------------------ | ------------------------------- |
| **task_id** | BIGINT / UUID    | **PK**, auto                                                       | Ідентифікатор                   |
| **user_id** | BIGINT / UUID    | **FK → User.user_id**, NOT NULL                                    | Власник завдання                |
| title       | VARCHAR(255)     | NOT NULL                                                           | Назва (пошук і фільтр за ім'ям) |
| description | TEXT             | NULL                                                               | Опис                            |
| status      | ENUM             | NOT NULL, default `todo`, CHECK in (`todo`, `in_progress`, `done`) | Статус (Feature 6)              |
| priority    | ENUM             | NOT NULL, default `medium`, CHECK in (`low`, `medium`, `high`)     | Пріоритет (Feature 7)           |
| due_date    | DATE / TIMESTAMP | NULL                                                               | Дедлайн (Feature 8)             |
| created_at  | TIMESTAMP        | NOT NULL, default now                                              | Дата створення                  |
| updated_at  | TIMESTAMP        | NOT NULL                                                           | Дата останньої зміни            |

### 2. Ключі

- **Первинні ключі:** `User.user_id`, `Task.task_id`.
- **Зовнішній ключ:** `Task.user_id → User.user_id`.
- **Альтернативний ключ:** `User.email` (UNIQUE).
- **Поведінка FK:** `ON DELETE CASCADE`, тобто при видаленні користувача видаляються й усі його завдання.

### 3. Зв'язки та кратність

**User 1 ─ 0..N Task** (один-до-багатьох)

- Користувач може мати від 0 до N завдань: щойно зареєстрований користувач ще не має жодного.
- Завдання належить рівно одному користувачеві, бо `user_id` є NOT NULL.
- Зв'язок ідентифікуючий не є: `task_id` має власний PK, а `user_id` у ньому не входить.

```text
┌──────────────┐ 1                 0..N ┌─────────────────┐
│     User     │────────────────────────│      Task       │
│──────────────│    "володіє"           │─────────────────│
│ PK user_id   │                        │ PK task_id      │
│ email (UQ)   │                        │ FK user_id      │
│ username     │                        │ title           │
│ password_hash│                        │ description     │
│ created_at   │                        │ status          │
└──────────────┘                        │ priority        │
                                        │ due_date        │
                                        │ created_at      │
                                        │ updated_at      │
                                        └─────────────────┘
```

### 4. Індекси для пошуку й фільтрації (Features 9-10)

- `(user_id, status)`: фільтр за статусом.
- `(user_id, priority)`: фільтр за пріоритетом.
- `(user_id, due_date)`: фільтр і пошук за датою.
- `(user_id, title)`: пошук за іменем. Для пошуку за підрядком (`LIKE '%...%'`) краще повнотекстовий або trigram-індекс.

Усі індекси починаються з `user_id`, бо кожен запит завжди обмежений поточним користувачем.

### 5. Рішення, які варто погодити

1. **Enum чи довідникові таблиці.** Я використав `CHECK`/ENUM, бо значення фіксовані й прості. Якщо набір статусів чи пріоритетів має змінюватися без міграцій, можна винести їх у таблиці `Status` і `Priority` (зв'язок 1:N з Task).
2. **Яку дату шукати та фільтрувати.** У специфікації не уточнено, чи це `due_date`, чи `created_at`. Модель підтримує обидва варіанти.
3. **Мʼяке видалення.** Feature 5 не вимагає історії, тому я лишив фізичне видалення. Якщо потрібне відновлення, додайте `deleted_at TIMESTAMP NULL`.

Можу також підготувати SQL DDL для PostgreSQL чи MySQL або намалювати ER-діаграму в Mermaid.
